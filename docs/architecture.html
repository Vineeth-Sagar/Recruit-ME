§1What the automation actually is

The repo README calls it an "AI-powered daily job alert system." That is accurate and worth stating plainly up front: it discovers and ranks jobs and emails you a report. It never logs into a job site as you and never submits an application. That single fact shapes most of the design and most of the legal questions below.

1.1  End-to-end behaviour

There is no server. The Git repo is the database, GitHub Actions is the scheduler and compute, and a Streamlit app on Streamlit Community Cloud is the settings UI. A run is one execution of job_hunter/main.py:

  1. Configure. The Streamlit app writes config.json and, on save, pushes it (and uploaded résumé PDFs) into the GitHub repo through the GitHub API using a Personal Access Token (GH_PAT). The repo is the persistence layer.
  2. Trigger. A cron workflow (daily_job_hunt.yml, 30 1 * * * UTC = 07:00 IST), or a workflow_dispatch fired from the app's "Test Run" page, checks out the repo and runs main.py.
  3. Load. load_config() parses config.json into dataclasses. Secrets come from Actions env vars: OPENROUTER_API_KEY, GMAIL_APP_PASSWORD, SERPAPI_API_KEY, GH_PAT.
  4. Parse résumés. PyMuPDF extracts text; an OpenRouter LLM (nvidia/nemotron-3-super-120b-a12b:free) returns structured JSON. The parse is cached back into config.json, keyed by a SHA-256 of the PDF bytes, to avoid re-spending free-tier quota on an unchanged file.
  5. Scrape. run_scrapers() runs enabled sources in a ThreadPoolExecutor (one thread per source, 300 s soft timeout) and merges results into a common job dict.
  6. Deduplicate. data/seen_jobs.db — a SQLite file kept in an Actions cache, not committed. Key is md5(company|title|source).
  7. Match. batch_match_jobs_against_all_profiles() sends batches of 20 jobs, one OpenRouter call per batch per résumé profile, temperature 0, time.sleep(6) between calls (free tier ≈ 10 RPM), exponential backoff on 429. If every job falls back to keyword scoring, the run emails an error alert instead of a misleading report.
  8. Report & send. build_excel() (openpyxl, 4 sheets) then send_report_email() over Gmail SMTP with an app password. The Actions job then commits config.json + data/reports/*.xlsx back to the repo.
  9. Review. Streamlit pages read those Excel files (local or via GitHub API) for the History and "Today's Matches" views; the Test Run page polls the Actions REST API with the PAT for live step progress.

1.4  Assumptions that break under concurrent users

  1. Repo-as-database rework

    Every write is a git commit + push. Concurrent users mean merge conflicts, serialized writes, unbounded history growth, and résumé PII permanently in history. There is no row, no transaction, no per-user isolation.

  2. GitHub Actions as the runtime rework

    2,000 minutes/month per account, one workflow file, a 45-minute job cap, and workflow_dispatch with no per-user isolation. It is not a job queue: no priority, no backpressure, no fair scheduling between tenants.

  3. One shared set of credentials rework

    One OpenRouter free key (global 10 RPM), one Gmail account (500/day + bulk-sender suspension risk), one SerpAPI quota, one egress IP. One aggressive user gets the shared IP blocked on Naukri/LinkedIn for everyone.

  4. Rate limiting via time.sleep(6) in the request path rework

    Fine for one nightly run. Across N users it serializes to roughly N × (jobs/20) × 6s of pure sleeping unless the limiter becomes a shared, per-key, non-blocking token bucket.

  5. Undocumented endpoints, spoofed headers, HTML selectors rework

    Private APIs change without notice; selectors rot; the hardcoded Wellfound Algolia key can be revoked. Doing this as a public product for many users is the single largest reliability and legal risk — see §3.

  6. Module-global LLM client fix

    _client in ai_engine.py caches the first key it sees. In a long-lived worker serving many tenants it would leak one tenant's key/config into the next request.

  7. No idempotency or safe retry design in

    A retried run re-scrapes, re-matches (re-spending LLM quota) and re-emails. mark_jobs_seen only fires after a successful email, so a crash just after sending produces duplicates next run.

  8. Global SQLite dedup file rework

    Single writer, date('now'), one file. Concurrent workers in separate containers cannot share it.

  9. Plaintext secrets in env vars rework

    No per-user isolation, no encryption at rest, no rotation. A multi-tenant product holding users' site credentials needs envelope encryption and a real secrets store.

  10. Résumé = a PDF on disk, parsed once rework

    Cached by file-hash in config.json. Needs object storage, a parse pipeline with status, versioning, and a real answer for image-only PDFs (they silently yield nothing today).

  11. Single IST cron; no per-user schedule design in

    Time zone and run time are baked into the workflow. Per-user schedules need an actual scheduler with locking.

  12. config.json read/write race resolved by DB

    The Streamlit app and the Actions run both write the same file; the code comments on the hazard. Two writers, no lock — gone once state is in Postgres.

§2Target architecture

A conventional three-tier SaaS: a Next.js front end, a FastAPI back end that only ever reads, writes and enqueues, and a pool of stateless workers that run the unchanged engine with one tenant's configuration injected as data. Postgres for relational state, Redis for the queue and rate-limit buckets, object storage for binaries.

2.3  Execution model

Automation never runs inside an API request. POST /runs validates, inserts a runs row as queued with an idempotency key, enqueues one message, and returns 202 Accepted with the run id. Everything else happens in a worker.

Queue & workers

  • Broker: Arq (async, Redis-backed, small). It fits FastAPI's async world and this IO-bound workload better than Celery; Celery is the fallback if you want the bigger ecosystem.
  • Separate queues / pools: scrape (high concurrency, IO-bound), match (low concurrency, LLM-quota-bound), default. They scale independently.
  • Scheduler: a one-minute beat process that finds job_profiles due by schedule_cron + timezone and enqueues runs, taking a Redis lock per profile so replicas don't double-fire.

Why not Temporal

The "multi-step apply flow" here is a single fan-out / fan-in batch — scrape N sources, score, persist, email — that finishes in minutes with no human-in-the-loop waits. Arq plus idempotent steps covers it. Revisit Temporal only if real auto-apply lands, with multi-day waits, approval gates, and per-application sagas.

2.4  Auth & RBAC

  • Passwords: argon2id. Access token: JWT, ~15 min, RS256 (front end and other services verify without the signing secret); claims sub, role, plan, jti.
  • Refresh token: opaque random, stored hashed in refresh_tokens, ~30 days, rotating — on reuse of a rotated token the whole family is revoked. Delivered as an httpOnly, Secure, SameSite=Lax cookie; the access token stays in memory only.
  • Endpoints: /auth/signup (+ email verification), /auth/login, /auth/refresh, /auth/logout, /auth/verify-email, /auth/forgot, /auth/reset.
  • RBAC scaffold: role = user | admin, plan = free | pro. Dependencies require_role() / require_plan() gate routes; admin endpoints are stubbed now (list/suspend users, view any run). Tenant isolation is enforced in the data layer regardless of role; admins reach tenant data only through explicit, audit-logged impersonation endpoints.

2.7  Scalability concerns, each answered

ConcernResponse
Horizontal worker scalingStateless arq workers scaled by replica count; autoscale on Redis queue depth (KEDA in k8s, or a metrics policy). scrape and match are separate pools with separate limits.
Per-user rate limiting vs. job sitesRedis token bucket keyed ratelimit:{site}:{user_id} and a global ratelimit:{site} ceiling. A worker acquires a token before each request or reschedules. One user cannot exhaust a site; the global cap protects the shared egress IP. Per-site politeness config: RPM, burst, min-delay, allowed hours.
Secrets managementApp secrets from environment / a secret manager, never the repo. User site-credentials use envelope encryption: a per-row data key wrapped by a KMS master key, rotatable via key_version; plaintext exists only in worker memory during a run, is never logged, and is never returned by the API.
Idempotency & retry for flaky sitesIdempotency key on run creation; per-source results upserted ON CONFLICT; notify gated by runs.notified_at; transient errors retried with backoff + jitter; a source that fails all retries yields a partial run rather than a failed one.
Engine ↔ config boundarypackages/engine is a pure library: run_engine(EngineInput) -> EngineResult, where EngineInput = {profile, resume_parses, enabled_sources, site_credentials, limits}. No DB, no auth, no scheduling, no network config. The worker builds the input from tenant rows and writes the result back. Same engine for every tenant.

2.8  Data storage

  • PostgreSQL — all relational state; jsonb for parsed-résumé and run-stats shapes; text[] for the many list fields config.json carried.
  • Redis — queue broker + result backend, rate-limit buckets, parse/dedup caches, per-profile run locks, refresh-token denylist.
  • Object storage (S3 / MinIO) — résumé PDFs, generated Excel reports, and future generated cover letters. Presigned URLs, lifecycle expiry on reports, versioning on résumés. This is where "object storage is needed" — binaries do not belong in Postgres and definitely not in Git.

2.9  Deployment

Local dev: one docker-compose.yml with postgres, redis, minio, api (uvicorn --reload), worker (arq), scheduler, web (next dev). Ships with .env.example, Alembic migrations on api start, and make seed for a demo user + profile + sample matches so the dashboard renders on first boot.

§3Terms-of-service & legal flags

The pattern across all of these: doing something for yourself is lower-risk than offering it to the public as a service, and covert is riskier than consensual. Most are now resolved (see the locked-decisions box up top); the rest are marked open.

  1. LinkedIn / Indeed / Glassdoor via python-jobspy decided · kept

    All three prohibit scraping and this is the highest ToS exposure in the set. Decision: keep it running now (it works today), but Phase 4 default is bring-your-own — the run only touches the big-3 for a user who has opted in via a consent screen and ideally supplied their own session, never covertly from a shared pool. Vetoable at Phase 4.

  2. Private APIs & HTML scraping — Naukri, Unstop, Wellfound, Cutshort, Internshala mostly decided

    Naukri and Unstop: dropped. Wellfound: kept on its borrowed public Algolia key — noted as a shared single point of failure if the key is rotated. Internshala & Cutshort: still open — same category as Naukri/Unstop, drop for consistency unless the student audience needs Internshala. YC jobs.json and the HN Algolia API are genuinely public — kept.

  3. Email sender decided

    Transactional provider as the platform sender — default Resend, behind a sender interface so SES / Postmark is a config swap. SPF/DKIM/DMARC on a verified domain, per-user unsubscribe. No Gmail, no per-user OAuth mailbox for v1.

  4. Storing users' job-site passwords or session cookies decide

    Even encrypted, holding LinkedIn/Naukri credentials and acting as the user can violate those sites' terms and carries real security and liability weight. Prefer: no stored third-party passwords; OAuth where offered; user-pasted short-lived tokens they can revoke; explicit per-site consent screens; and a clear framing that the platform is a tool the user operates, not a covert bot farm.

  5. Proxy / rotating-IP scraping to dodge blocks decide

    This crosses from "automating my own browsing" into "evading access controls." Decide explicitly and document it. The defensible posture: respect robots.txt and published rate limits, identify the bot honestly, prefer official APIs, and require user consent + user credentials for anything gated.

  6. Résumé PII in public Git history migrate

    A real résumé with CGPA and project detail is committed to the current public repo. In the SaaS, PII lives only in Postgres / object storage with encryption, access control, deletion-on-request (GDPR / India DPDP), and an actual privacy policy.

  7. Licensing choose

    Since it's a hosted service, AGPL-3.0 keeps hosted forks open; MIT maximises adoption. Draw a clean line between the open engine and any hosted-only pieces (billing, admin).
